# H3 内容大纲规划

输入是原始用户要求、解析后的要求、`media_analysis` 和目标时长。先决定视频展示什么，再交给分镜决定怎样拍。原始用户要求优先；解析结果只帮助整理，不能把推测变成用户要求。

## 第一步：分清要求、素材和创作

在 `creative_brief` 中区分：`user_locked` 是用户明确指定的内容；`reference_anchors` 是素材提供的身份、外观、状态或过程；`open_design` 是尚未指定、允许创作的部分。用户只描述一个片段时，不自动限制整部视频。严格复刻、局部修改和指定首尾帧按用户范围保留。

把用户要求写入 `requirement_map`，每项有稳定 ID 和准确文本：`content_events` 记录动作或展示内容，`editing_treatments` 记录切镜和视觉效果，`global_style` 记录整体风格，`audio_requirements` 记录声音要求。分类不能改变顺序、扩大范围或漏掉要求。

素材分析说明实际看见或听见了什么。静态图不能证明动作、先后或声音。文字若表达了故事信息，规划时考虑其含义；装饰文字只作为设计内容。合理补全可以写进目标视频，但不能说成素材中已经发生的事实。

## 第二步：安排内容和结束位置

确定视频主要让观众看见什么变化。涉及动作时，选定谁执行、谁受到影响，以及动作怎样从开始发展到本片的结束位置。主体的动作要可见：哪个部位开始工作或移动，物体怎样运动，周围怎样响应。不要用整幅画面变亮、震动或冲击声代替动作本身。用户未指定的细节在允许范围内具体设计，不另起无关剧情。

按目标时长决定内容能展开到哪里。可以表现完整事件，也可以只表现其中一段；用户没有要求完整结局时，可以在高潮或直接结果处结束，不必再恢复平静、返回参考构图或增加结束卡。删除重复表演，给有用的动作、细节和变化足够展示时间。明确要求太多而无法容纳时，记录具体冲突，不暗删要求。

区分先后和同时：必须先发生的动作保持顺序；能够一起呈现的主体动作、环境反应和文字效果可同时发展。不要按用户列举词语的顺序把每种效果排成独立段落。文字、图形或抽象变化本身是主题时，围绕它们组织内容，不强加人物故事。同一版式的主副标题作为一次完整展示，可以依次出现，不自行插入别的事件。

## 第三步：写 developments

每条记录一个有意义的内容发展，包含 `id`、`source_content_event_ids`、`visible_change` 和 `outcome`。`visible_change` 写执行者、可见过程和同时发生的相关变化；`outcome` 写这一段结束时已经到达的状态，动作尚未完成就如实写仍在进行。要求 ID 引用实际对应的要求。

服务同一目标的准备、执行、即时反应和直接结果通常放在同一条中。换角度、增强闪光或重复展示同一状态不另建 development。只有新的内容、关系、结果或时空变化才另起一条；不在这里写镜头数、机位或切点。

后续发展接上已经发生的变化。逐条核对谁做了什么、物品在哪里、由谁持有、动作是否完成；离开、拿走或改变的主体不能无过程地恢复原状。切黑和文字出现不重置状态。保持用户指定的动作类型、执行主体、群体范围以及依次或同时的关系。

## 第四步：说明素材怎样使用

发展链确定后填写 `bindings`：`asset_id`、`role`、`retained_attributes`、`optional_inherited_attributes`、`excluded_attributes` 和 `exclusion_reasons`，同时写定 `reference_anchors`。素材提供外观、环境或构图，不等于用户要求它成为首帧或尾帧。

用户点名保留的属性写准确并说明适用阶段；要求修改的目标值写进 `user_locked`，被替换的原值放进 `excluded_attributes`。无法辨认的属性不猜写。固定身份可以贯穿全片，位置、开合和持物状态随事件更新，不写成永久保留。只有需要独立控制的对象才单列，不把每个背景细节都拆成主体。

## 检查与交接

输出 `creative_brief`、`requirement_map`、`developments` 和 `bindings`，不另建 `must_keep`。交接前核对：明确要求没有遗漏；主要过程可见；结尾与此前状态一致；补充内容能放进目标时长。把已确定的内容交给分镜；分镜可安排同时发生的画面和观看方式，不改变指定动作及结果。
